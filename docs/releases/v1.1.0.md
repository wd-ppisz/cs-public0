# cs-public0 1.1.0

Release date: 2026-11-11. Tag: **`v1.1.0`**.

This release consolidates optional automatic DROP qualification, outbound traffic
observation, IP/IOC feeds and passive DNS detection. The base installation still
requires explicit activation, an operator-supplied Suricata engine and a reviewed
ruleset. The tag identifies specific source code; it does not enable new features
on existing hosts.

## Changes since 1.0

### 1. ALERT-to-DROP rule qualification

- The optional controller uses fresh CISA KEV and FIRST EPSS data. KEV is a CVE
  catalog, not a ready-made list of Suricata rules.
- Promotion requires matching engine, source rules, SID/revision and replay
  corpus identities. A rule must match a positive case without matching the
  legitimate or outbound test cases. An unknown result does not authorize DROP.
- `technology_profile` limits new candidates to explicitly protected technologies
  and visible protocols. A web profile can cover Apache, nginx/PHP, Laravel,
  Drupal, GitLab, Grafana and React Server Components/Next.js. A Fortinet/Java
  example in the general corpus does not qualify it for an arbitrary stack.
- Batch limits, a daily cadence, guarded activation, a ten-minute canary, sensor
  identity checks and history preservation remain in place. The local profile
  and the optional external-probe profile have different acceptance scopes.

See [automatic policy](../automatic-exploit-policy.md),
[rule activation](../activation-controller.md) and [blocking policy](../blocking-policy.md).
The number of DROP rules depends on qualification in each installation. This
release does not prescribe eight rules or claim complete KEV or exploit-variant
coverage.

### 2. Egress observation and data integrity

- The collector runs outside the packet path and reads EVE alert/flow/stats
  records. It preserves a durable cursor, bounded database, counters and SHA256
  references to source records.
- Direction comes from initiation evidence in a correlated flow. An IP pair, a
  reply to a scan or `to_server` alone does not prove VM-initiated traffic.
  Insufficient evidence remains `unknown`; SNAT does not identify an individual VM.
- Classification revision 2 treats IPInsights solely as ingress-source reputation
  context. It does not turn that feed into evidence of scanning, C2 or outbound
  abuse. Independently qualified signatures and other IOC sources remain distinct.
- New counters do not import legacy noise. Historical counters, cursors and
  evidence are retained. Repeated observations are not unique attack counts.

See the [egress contract, metrics, retention and direction](../egress-security.md).

### 3. IP feeds and DROP inventory

- The updater separates HTTP fetch time, source publication time, indicator
  validity, content version and the last successful application in the kernel.
- Only IPsum level 3 and Spamhaus can contribute reputation-based blocking: an
  initial TCP SYN from a listed source to an explicitly protected network on the
  selected bridge. SYN/ACK replies, ACK/data, UDP, ICMP and VM egress pass this
  layer. The `outgoing` and `c2_ports` sets remain empty.
- IPInsights, ThreatFox, Feodo, FireHOL and optional OTX supply detection context.
  An expired source does not become fresh merely because HTTP returns 200.
  Required keys and site configuration belong to the operator, outside this
  public repository.
- Application uses an atomic nft transaction and checks table ownership,
  expressions, types and actual elements. Failures retain explicit outcomes and
  evidence.
- Growth limits compare against a still-valid, nonempty predecessor. TTL renewal
  now prevents a nearly expired feed from shortening protection provided by other
  sources. Blocking entries have bounded lifetimes and also expire if the updater
  stops.
- The inventory publishes exact SID/revision/CVE identities from the confirmed
  ruleset. Unknown historical fetch times remain unknown instead of using mtime.

See [sources, direction, TTL and acceptance](../ip-intelligence.md).
Suricata rules have a separate lifecycle. Empty reputation-based egress sets do
not remove existing, explicitly selected IPS signatures.

### 4. Passive DNS IOC

- A separate Suricata process passively captures plaintext DNS over UDP/TCP port
  53, without NFQUEUE or signature detection. It does not restart the inline sensor.
- The collector compares the exact EVE v3 DNS query name with current ThreatFox
  domains, preserving IOC provenance and source-event evidence.
- Metrics distinguish source freshness, IOC freshness, backlog, continuity and
  loss history. Rotation, producer boundaries, SQLite/outbox behavior and resource
  bounds remain explicit.
- A match means a DNS query was observed, not that infection or a successful C2
  connection was confirmed. DNS over HTTPS/TLS, DGA, RPZ and sinkholing are outside
  this module's scope.

See [DNS IOC installation, evidence and rollback](../dns-ioc.md).

## Upgrading an existing installation

1. Select one host and pin the tag/commit, engine, configuration and rule sources.
   Retain previous artifacts, state, counters, database/cursor and sensor identity.
2. Read the [installation guide](../installation.md) and verify current pins.
   Rerunning the full `ansible/site.yml` stops the managed sensor. A restart-free
   upgrade requires a separate, compatible migration procedure for that component.
3. Install a new immutable bundle and new configuration. Stop future ticks of the
   affected consumer, wait for the current process to finish, use the existing
   lock and retain the migration intent. Do not edit code under an old pin.
4. Make the reader compatible with the new IOC format first. When changing the
   updater parser, update its pin in the DNS reader and the service configuration
   hash. Do not leave producers and consumers with different contracts.
5. HOLD, an active attempt and an unknown activation outcome require separate
   diagnosis. A release or version change does not erase history or approve a
   new baseline.
6. After resuming, verify a natural tick, current sources, actual nft state, rule
   inventory, fresh metrics/logs and legitimate traffic. Proceed to the next host
   only after accepting the canary and the relevant service probes.

Maintain Prometheus/Grafana integration, log transport, notifications, the private
technology profile and operator inventory in your own IaC. The public package
does not include customer configuration, private secrets, third-party rulesets or
their licenses.

## Known limitations and acceptance scope

**The NFQUEUE/fail-open limitation from 1.0 still applies to 1.1.** Queue pressure
can forward packets without inspection, including cases with zero exported Drops.
A larger netlink receive buffer does not solve packet-queue saturation. A healthy
process, passing tests and a current zero-loss reading do not prove complete
inspection.

[G6](../g6-acceptance.md), representative workload cost, latency, retransmissions
and full acceptance of a physical installation remain separate requirements.
HTTP signatures do not decrypt HTTPS; HTTP SQL injection protection does not imply
inspection of native MySQL/PostgreSQL traffic. IPv6 and missing exploit variants
remain outside the declared coverage. Follow the [security policy](../../SECURITY.md),
[NFQUEUE diagnostics](../nfq-receive-buffer.md) and [rollback procedure](../rollback.md).

Unit tests, root-only tests and separate dataplane/DNS integrations have distinct
prerequisites. Exit code 77 or SKIP means a check was not performed. Passing CI
does not replace a canary on your own hardware or turn an IOC match into confirmed
abuse.
